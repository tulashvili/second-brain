# Стиль заметок SECURITY

## Доступ к исходным заметкам

- Источник истины для заметок и вложений — vault `content` в Ignis: `http://192.168.1.122:8081`. Читать актуальный контент через API, а не через Personal MCP, локальную копию Obsidian или старый checkout.
- Использовать пользовательскую авторизованную сессию: вход `POST /api/auth/login`, список хранилищ `GET /api/vault/list`, дерево `GET /api/fs/tree?vault=content`, чтение файла `GET /api/fs/readFile?vault=content&path=<URL-encoded path>`. Для текста можно передать `encoding=utf8`; вложения читать как байты.
- Cookie хранить во временном файле вне репозитория; не записывать логин, пароль, cookie или путь конкретной сессии в правила, Git и журналы. При истечении сессии запросить новую у пользователя.
- Локальный снимок из API используется только для подготовки и проверки сборки. Перед публикацией проверить, что исходные заметки не изменились. Изменения исходных заметок выполнять через Ignis API только в пределах поручения пользователя.
- Эти `AGENTS.md` и `WRITING-STYLE.md` сохранены локально в `my_ansible/playbook/second_brain/content-rules/`. В vault `content` на момент проверки этих файлов нет. Если там появятся дополнительные правила, прочитать их через API перед работой с соответствующими заметками.

## Цель

Помогать читателю быстро понять основную мысль, увидеть пример и найти ограничения или способ проверки. Сохранять авторский голос: личный опыт, конкретные наблюдения и исходные формулировки важнее единообразного шаблона.

## Как оформлять содержательную заметку

1. Начать с короткого `> [!tldr] Коротко` (в английской паре `In brief`): одна конкретная мысль из текста, без обещаний и общих фраз. Не повторять его дословно в конце.
2. Разбить материал на разделы по смыслу. Заголовки называют предмет раздела: «Как работает», «Пример», «Ограничение», «Проверка». Не добавлять пустые разделы ради шаблона.
3. Использовать существующий пример, схему, команду или наблюдение. `> [!example]` подходит для короткого примера; длинные команды и журналы оставлять отдельными блоками кода.
4. Выносить существенное ограничение, риск или практическую оговорку в `> [!note]` или `> [!warning]`. Один callout — одна мысль. Не превращать каждый абзац в admonition.
5. Завершать коротким «Итого» только там, где оно помогает собрать несколько идей. Итог не должен пересказывать всю заметку или вводить новую тему.

## Что сохранять

- Не перефразировать существующие утверждения ради оформления. Допустимы заголовки и короткие связки, если без них структура не читается.
- Не выдумывать примеры, результаты команд, проверки, угрозы или выводы. Новые фактические утверждения требуют отдельной проверки источника.
- Сохранять код, изображения, wikilinks, внешние ссылки, личный опыт и порядок шагов. Если текст содержит сомнительное утверждение, отмечать его для проверки отдельно от форматирования.
- Для короткого определения или навигационной заметки не навязывать `tldr`, пример, admonition и итог одновременно. Навигационные заметки остаются каталогами ссылок.

## Две локали и публикация

Для публичной русской заметки обновлять английскую пару в том же изменении. Сохранять `translationKey`, маршруты, ссылки и вложения; переводить новые заголовки и короткие добавления по смыслу. Перед выпуском выполнять проверки из `AGENTS.md` и `CONTENT_DEPLOY_PIPELINE.md` в репозитории Ansible.
